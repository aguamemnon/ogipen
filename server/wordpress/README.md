# WordPress offline workstation activation — v0.4.6

This companion extends the existing WordPress SLM Plus multi-software fork. WordPress remains the only licence issuer; no private signing key or signing service is installed on Ogipen's Linux server.

## Deployed workflow

The existing **SLM Plus → Ogipen hors ligne** page now has two tabs:

1. **Licence serveur** retains the deployed `ogipen-license-v1` server export and its existing import path in the PHP portal.
2. **Activer un poste (.ogreq)** accepts a request generated by `OGIPEN.Core.Security.OfflineLicenseActivation.CreateRequest`, verifies its P-256 proof and issues the `OGIPEN-OFFLINE-LICENSE` / `ES256-DER` wrapper expected by the existing C# `TryImport` verifier.

Choose an active, identity-verified beneficiary of an active SLM Plus licence, upload the `.ogreq`, and select an offline duration from 1 to 365 days. Expiration is capped by the commercial licence. Rights and modules are read from SLM Plus, never from an uploaded request. The workstation proves possession of its private key; the key itself is never uploaded.

This first workflow is administrator-only and nominative, with one active public-key installation per beneficiary. Site licensing and contractual multi-workstation rules are not implemented by this release. The verified-beneficiary requirement is retained; no real beneficiary is silently created or marked verified.

## Request and activation controls

- Exact request schema and canonical base64url are required; maximum request size is 8 KiB.
- The software, major version, nonce, SPKI public key and DER proof match the existing client's canonical request text.
- Public keys are restricted to canonical P-256 SPKI. Extra identifying fields, modified proofs, malformed keys and oversized inputs are rejected.
- The parent licence row is locked, using the same allocation lock as beneficiary and quota changes.
- A global unique nonce hash prevents request reuse across contexts. Retrying the same eligible request returns its recorded file without creating another activation. Changed rights, replaced grants, revocation or expiry prevent replay.
- A new request from the same key can renew and replace its earlier grant. A different key requires explicit revocation of the previous activation. One key cannot represent two beneficiaries of the same licence.
- Issuance, stored signature and audit commit together. An audit failure rolls back the grant.
- Retained activation history includes beneficiary/licence IDs, public-key fingerprint, nonce/request hashes, actor, dates, state and signed file. Raw requests, private keys and machine/user identifying details from the request are not stored.
- Download and revocation require administrator capability, POST and an activation-specific nonce. Revocation requires a reason. As with any offline licence, a previously imported file cannot be revoked instantly without connectivity; it remains valid until its expiration.

## Files and dependencies

Install the two PHP companions from `mu-plugins/` in the existing WordPress MU-plugin directory. They require the already deployed SLM Plus multi-software fork (`slmms_table`, its licence and beneficiary tables) and the existing protected P-256 signing key outside the web root. No keys, real licences or operational configuration are in Git.

The new companion creates its versioned `slmms_offline_activations` table during administrator initialisation. Back up the WordPress database, existing MU plugins and signing-key configuration before upgrading. Preserve existing licences and the older server-export companion.

The PHP administration portal only imports **server** licences; a small view clarification links users to the correct WordPress tab. A workstation `.oglic` belongs in the C# client, not the PHP server licence importer.

## Verification

The release passed 35 WordPress request/issuance/history/security controls, 8 interoperability checks against the existing C# verifier and 7 server-export regression checks (50 in total). WordPress tests used connection-local temporary shadow tables; actual licences and beneficiaries were unchanged, and no real activation was retained. The interoperability key and signed fixture were temporary and removed after testing.

The C# checks reference `src/OGIPEN.Core/Security/OfflineLicenseActivation.cs` from the repository when built in-tree. The remote test used an exact snapshot of that existing file, not a replacement verifier written to fit the new issuer. The Windows UI and CNG key store were not exercised on an actual workstation in this release.

The next integration work is the real client's OS-session binding, authorised enrolment and pinned issuer-key provisioning. No project creation from PHP, business screens or second licence issuer is introduced here. Direct HTTPS on port 8080 remains deferred at the user's request.
